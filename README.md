# Health1st Clinic Voice Agent

An AI voice agent that answers a clinic's phone line and handles appointment booking, rescheduling, and cancellation end-to-end — built from first principles (no-code voice platforms explicitly excluded), with the conversation logic validated in text before any voice layer was added.

---

## What it does

- Answers inbound calls via Twilio, in real time
- Books, reschedules, and cancels appointments against a real SQLite-backed clinic schema (providers, appointment types, availability)
- Answers clinic FAQ questions (insurance, hours, location, policy) grounded in a RAG knowledge base — never fabricates an answer it doesn't have
- Hard-routes any medical/symptom question to a fixed, non-improvised safety redirect — never gives medical advice
- Handles real barge-in (caller talking over the bot) without falsely triggering on background noise or a caller simply speaking after a pause
- Speaks with natural, phone-appropriate phrasing — no markdown, no machine-formatted dates read aloud
- Auto-captures caller ID, so "use the number I'm calling from" just works
- Live, auto-refreshing appointments dashboard for demo/monitoring

## Architecture

```
Caller ──Twilio──▶ FastAPI /ws (Pipecat pipeline)
                       │
        ┌──────────────┼───────────────────────────┐
        ▼              ▼                            ▼
   Deepgram STT   SafetyGate (hard-routed)    InterruptionGate
   (streaming)    narrow classifier LLM       real barge-in only
        │              │                            │
        └──────────────┴───────────┬────────────────┘
                                    ▼
                          OpenAI LLM (gpt-5.4-nano)
                          + native tool-calling
                                    │
                    ┌───────────────┼────────────────┐
                    ▼               ▼                ▼
              Booking tools    RAG (Chroma)     Filler phrases
              (SQLite)         clinic FAQ       (tool-selective)
                    │
                    ▼
              Cartesia TTS (streaming) ──▶ Twilio ──▶ Caller
```

Two separate implementations exist in this repo, reflecting a real architecture decision made mid-project (see docs for the full reasoning):

| | Status |
|---|---|
| **`langgraph_app/`** — text-first conversation logic, LangGraph orchestration | Complete, fully tested in text. Not wired into a live real-time voice pipeline. |
| **`pipecat_app/server_tools_test.py`** — native Pipecat tool-calling | **This is the working, demoable system.** Real-time, streaming, deployed against live calls. |

The native-Pipecat path was chosen over running LangGraph inside the live audio loop after measuring unacceptable latency with local STT/TTS and reasoning that LangGraph's per-call state overhead was an unnecessary risk to add before proving the simpler path worked. This tradeoff — and the real, measured numbers behind it — is documented in full in the accompanying report.

## Tech stack

| Layer | Choice | Why |
|---|---|---|
| Telephony | Twilio (Media Streams) | Standard webhook + WebSocket approach, full code control |
| Voice pipeline framework | [Pipecat](https://github.com/pipecat-ai/pipecat) | First-class Twilio transport, runs in-process, no separate media server |
| STT | Deepgram (`nova-3`, streaming) | Streaming from the first byte; local Whisper was tried first and rejected — see docs |
| TTS | Cartesia (`sonic-2`, streaming) | Streaming, natural voice; local Piper was tried first and rejected — see docs |
| LLM | OpenAI `gpt-5.4-nano` | Tool-calling, low latency, `reasoning_effort: none` for conversational turns |
| Orchestration (text-first prototype) | LangGraph | State-graph model, native `interrupt()`, hard-routed branching |
| Database | SQLite | Full control over clinic-specific availability logic, zero external dependency |
| RAG | Chroma + `text-embedding-3-small` | Local vector store, grounded FAQ answers |

## Setup

### 1. Clone and install

```bash
git clone <this-repo-url>
cd Health1st-voice-agent
python -m venv venv
venv\Scripts\activate      # Windows
# source venv/bin/activate   # macOS/Linux

pip install -r requirements.txt
pip install "pipecat-ai[deepgram,openai,cartesia,silero]" fastapi uvicorn python-dotenv python-multipart websockets
```

### 2. Environment variables

Copy `pipecat_app/.env.example` to `pipecat_app/.env` and fill in:

```
TWILIO_ACCOUNT_SID=
TWILIO_AUTH_TOKEN=
DEEPGRAM_API_KEY=
OPENAI_API_KEY=
CARTESIA_API_KEY=
CARTESIA_VOICE_ID=          # optional, defaults to a standard voice
```

### 3. Build the database and RAG index

```bash
python db/seed.py
cd rag && python build_index.py && cd ..
```

### 4. Run the real pipeline

```bash
cd pipecat_app
uvicorn server_tools_test:app --port 8000 --reload
```

In a separate terminal:

```bash
ngrok http 8000
```

Point your Twilio number's "A call comes in" webhook (HTTP POST) at:
`https://<your-ngrok-domain>/twiml`

Then just call the number.

### 5. Watch it work

- Live appointments: `http://localhost:8000/dashboard`
- Terminal logs show `[latency]`, `[tool-call]`, `[safety-gate]`, and `[interruption-gate]` lines for every turn — useful for debugging or demoing what's happening under the hood.

## Testing without a phone call

```bash
cd pipecat_app
python test_local_call.py
```

Simulates Twilio's Media Streams protocol against a running local server — validates connection handling and pipeline construction without spending a real call.

To test conversation logic alone, with no voice/telephony at all:

```bash
cd langgraph_app
python run_text.py
```

## Known limitations

Documented in full, with reasoning, in `docs/Health1st_Documentation.docx` — summarized here:

- **Single call at a time.** STT/TTS connections are constructed fresh per call; no connection pooling or concurrency support yet.
- **Background-noise sensitivity is mitigated, not solved.** VAD thresholds are tuned to reduce (not eliminate) false triggers from voices near the caller — a single mono phone audio stream has no way to fully distinguish speakers without true diarization.
- **Confirmation gating is prompt-level in the live pipeline**, not hard-enforced by a state machine the way the LangGraph prototype's `awaiting_confirmation` flag was designed to be.
